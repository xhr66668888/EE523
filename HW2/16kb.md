## Issue 1 — Android 16 KB Page Size Compatibility Warning

### Symptom

Upon installing the APK on a device, Android displayed an **"Android App Compatibility"** dialog:

> This app isn't 16 KB compatible. ELF alignment check failed. This app will be run using page size compatible mode. For best compatibility, please recompile the application with 16 KB support.
>
> The following libraries are not 16 KB aligned:
> - `lib/x86_64/libimage_processing_util_jni.so` : LOAD segment not aligned
> - `lib/x86_64/libandroidx.graphics.path.so` : Unknown error

### Root Cause

Android 15+ requires native `.so` libraries' ELF `LOAD` segments to be aligned to **16 KB page boundaries** on devices that use a 16 KB page size. Three things were working against this project:

1. **Outdated CameraX (`1.3.0`)** — CameraX began shipping 16 KB-aligned native libs in `1.4.0`. `libimage_processing_util_jni.so` in `1.3.0` was aligned to 4 KB.
2. **Outdated `graphics-path` native lib** — pulled in transitively through `androidx.compose.ui:ui-graphics-android:1.7.6`.
3. **`useLegacyPackaging = true`** in `app/build.gradle.kts` — this forced native libs to be compressed inside the APK and extracted on install. Legacy packaging bypasses the alignment guarantees that modern AGP applies when libs are packaged uncompressed.

### Fix

Edits to [`app/build.gradle.kts`](SwapSense2025%20copy/app/build.gradle.kts):

```kotlin
// Before
implementation("androidx.camera:camera-camera2:1.3.0")
implementation("androidx.camera:camera-lifecycle:1.3.0")
implementation("androidx.camera:camera-view:1.3.0")

packaging {
    jniLibs {
        useLegacyPackaging = true
    }
}
```

```kotlin
// After
implementation("androidx.camera:camera-camera2:1.4.1")
implementation("androidx.camera:camera-lifecycle:1.4.1")
implementation("androidx.camera:camera-view:1.4.1")
implementation("androidx.graphics:graphics-path:1.0.1")

packaging {
    jniLibs {
        useLegacyPackaging = false
    }
}
```

### Verification

After rebuilding, extracted the APK and inspected `LOAD` segment alignment with `readelf -lW`:

```
=== lib/x86_64/libandroidx.graphics.path.so ===
  LOAD   ...   R E  0x4000
  LOAD   ...   RW   0x4000

=== lib/x86_64/libimage_processing_util_jni.so ===
  LOAD   ...   R E  0x4000
  LOAD   ...   RW   0x4000

=== lib/x86_64/libsurface_util_jni.so ===
  LOAD   ...   R E  0x4000
  LOAD   ...   RW   0x4000
```

`0x4000 = 16384 = 16 KB` — all native libs are now 16 KB aligned. The compatibility dialog is gone.

## Issue 2 — App Crashes on Launch (Flashes Black Screen → Wallpaper → Crash)

### Symptom

After fixing the alignment issue and installing the new APK, the app flashed a black screen, then the wallpaper, then another black screen, and crashed before showing any UI. `adb logcat *:E` showed:

```
FATAL EXCEPTION: main
Process: com.example.swapsense
java.lang.RuntimeException: Unable to start activity ComponentInfo{com.example.swapsense/com.example.swapsense.MainActivity}
 ...
Caused by: android.view.InflateException: Binary XML file line #31 in
  com.example.swapsense:layout/activity_main: Error inflating class
  androidx.fragment.app.FragmentContainerView
Caused by: java.lang.IllegalStateException:
  no start destination defined via app:startDestination for
  com.example.swapsense:id/mobile_navigation
    at androidx.navigation.NavGraphNavigator.navigate(NavGraphNavigator.kt:71)
```

### Initial Wrong Hypothesis

The obvious interpretation was that `mobile_navigation.xml` was missing a `startDestination`. But the file clearly had:

```xml
<navigation ...
    android:id="@+id/mobile_navigation"
    app:startDestination="@id/dashboardFragment">

    <fragment android:id="@+id/dashboardFragment" ... />
    ...
</navigation>
```

Downgrading `androidx.navigation` from `2.8.5` to `2.7.7` did **not** fix the crash — confirming this was not a Navigation-library regression.

### Real Root Cause — a Silent XML Namespace Typo

Dumping the compiled binary XML inside the APK with `aapt dump --values xmltree`:

```
N: android=http://schemas.android.com/apk/res/android
N: app=http://schemas.android.com/res-auto                    ← WRONG
  E: navigation
    A: android:id(0x010100d0)=@0x7f080126
    A: app:startDestination=@0x7f080094                       ← no attr ID!
```

Two things stood out:

1. The `app` namespace was declared as `http://schemas.android.com/res-auto` — missing the `apk/` prefix. The correct URI is `http://schemas.android.com/apk/res-auto`.
2. Notice `android:id(0x010100d0)` has a resolved attribute ID in parentheses, but `app:startDestination` has **no attribute ID**. AAPT could not bind the attribute to the `startDestination` attr defined inside the Navigation library.

At runtime, `NavGraph.onInflate()` calls:

```kotlin
context.resources.obtainAttributes(attrs, R.styleable.NavGraphNavigator).use {
    startDestinationId = it.getResourceId(
        R.styleable.NavGraphNavigator_startDestination, 0
    )
}
```

Because the XML attribute was never bound to the real attr, `getResourceId(..., 0)` returned `0`. That made `startDestinationId == 0`, which caused `NavGraphNavigator.navigate()` to throw `IllegalStateException: no start destination defined` — even though the XML looked correct to the human eye.

AAPT had logged **no warning or error** about the malformed namespace.

### Fix

One-character fix in [`app/src/main/res/navigation/mobile_navigation.xml`](SwapSense2025%20copy/app/src/main/res/navigation/mobile_navigation.xml):

```diff
- xmlns:app="http://schemas.android.com/res-auto"
+ xmlns:app="http://schemas.android.com/apk/res-auto"
```

Navigation was also restored to `2.8.5` (the downgrade had been unnecessary).

### Verification

After rebuilding, the compiled XML now shows a properly bound attribute:

```
N: app=http://schemas.android.com/apk/res-auto
  E: navigation
    A: android:id(0x010100d0)=@0x7f080126
    A: app:startDestination(0x7f030405)=@0x7f080094     ← attr ID now present
```

On relaunch, no `FATAL EXCEPTION` is thrown. Logcat shows `DashboardFragment` successfully loaded and raised its sensor-permission Toast — confirming Navigation reached the start destination. The subsequent process termination observed in the emulator was caused by `lowmemorykiller` due to the AVD's limited RAM, unrelated to the app.

---

## Takeaways

- **Silent XML namespace typos are brutal** — a missing `apk/` produced a runtime error whose message (`"no start destination defined"`) actively pointed at the wrong file. Looking at attribute-ID binding in the compiled binary XML (`aapt dump --values xmltree`) is the fastest way to catch this class of bug.
- **The 16 KB alignment warning and the crash were independent issues.** Fixing the first was a real change (CameraX upgrade + packaging flag). Fixing the second was a one-character correction to a namespace URI.
- **When a framework throws an exception that contradicts what the source file says, suspect the compiled artifact, not the library.**
